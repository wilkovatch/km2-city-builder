# Core Terrain Patches

A terrain patch is a polygon drawn by the user (usually snapped to the edges of roads and intersections) and filled with a textured, triangulated surface. Patches can have internal points (to shape hills). Walls and railings along their outline are not part of the patch: a core makes them spline custom elements that follow the perimeter (see [Core Custom Elements](Core-Custom-Elements#following-the-connections)).

The surface itself is generated by the program; the core defines the patch parameters and the UV scale, and can add meshes made from the surface with a [Lua script](Core-Lua-Scripts) (see `geometry` below).

```
terrainPatches/
└── terrainPatches/<type>/
    ├── ui.json
    ├── parameters.json
    └── settings.json
```

## Terrain patch types

### `parameters.json`

Same format as for other elements (see [Parameters and UI](Parameters-and-UI)). Patches have no per-section evaluation, so only static definitions are meaningful. Required definitions:

| Variable | Description |
|---|---|
| `uMult`, `vMult` | UV scale: the UVs of the surface are the world X and Z coordinates multiplied by these values. |

Patch parameters cannot be `instanceSpecific`. Built-in state properties (edited in `mainGroup`): `type`, `texture` (the surface texture; an empty texture makes the patch invisible), `smooth` (smoothing iterations of the internal vertices) and `projectToGround`.

Terrain patches have no presets: a new patch gets the first terrain patch type (in folder order), the last texture used, projection enabled, no smoothing, and every core parameter at its zero value (0, false, empty). Choose parameter meanings so that these values are a sensible default.

The MM2 core uses patch parameters only for its exporter (block number, merging connected patches, perimeter-only patches...): every parameter is part of the patch state in the exported file, whether or not it affects the geometry.

### `settings.json`

The file can be an empty object (`{}`). Optional settings:

| Setting | Description |
|---|---|
| `geometry` | `<module>.<function>` of the `lua` folder of the core: meshes added to the surface of the patch, e.g. a bottom under an elevated patch. Called after the surface is generated, at every rebuild of the patch. |

The function is called as the [script definitions](Core-Lua-Scripts), with `v` (the parameters and static definitions of the type) and `ctx`:

| `ctx` | Content |
|---|---|
| `typeName`, `name` | The type and the name of the patch. |
| `parameters` | A detached snapshot of the state of the patch (also the strings, e.g. the textures, which `v` doesn't have). |
| `surface` | The surface generated by the program: `vertices` (`vec3`), `uvs` (`vec2`) and `triangles` (a flat list of indices from 0 into `vertices`, three per triangle, of all its submeshes). |
| `perimeter`, `internalPoints` | The points of the patch (`vec3`). |

It returns `{meshes}`, in the format of the meshes of the [custom elements](Core-Custom-Elements#geometry): `texture` (a texture parameter of the patch, or a built-in material) or `color`, `vertices`, `uvs`, `triangles` (clockwise when seen from their visible side). `pickOnly` and `placeholder` meshes are ignored. The meshes are added to the mesh of the patch after the submeshes of the surface, one submesh each in their order, so they are in the exported mesh too, where an exporter can tell them from the surface; they are also part of its collider. An error in the script is reported and the patch keeps only its surface.

Example (the Midtown Madness 2 core: with `forceBottom` and a `bottomTexture`, the surface 1 m lower and facing down, which its exporter writes as a PKG mesh):

```json
{ "geometry": "terrainPatches.geometry" }
```

```lua
function M.geometry(v, ctx)
    local texture = ctx.parameters.bottomTexture
    if not v.forceBottom or texture == nil or texture == "" then return {} end
    local surface, down = ctx.surface, vec3(0, -1, 0)
    local vertices, triangles = {}, {}
    for i, p in ipairs(surface.vertices) do vertices[i] = p + down end
    local t = surface.triangles
    for i = 1, #t - 2, 3 do -- the other way round: seen from below
        triangles[#triangles + 1] = t[i]
        triangles[#triangles + 1] = t[i + 2]
        triangles[#triangles + 1] = t[i + 1]
    end
    return { meshes = { { texture = "bottomTexture", vertices = vertices, uvs = surface.uvs, triangles = triangles } } }
end
```

### `ui.json`

Built-in group: `mainGroup` (type, point placement mode, last point deletion, smoothing, projection, auto-close, texture).

## Border meshes (removed)

Patches used to have border meshes: road-like meshes along a chosen part of their perimeter, with their own types in `terrainPatches/borderMeshes/` and presets (`terrainPatchBorderMesh`). They are replaced by spline custom element types following the connections, which can also go along roads and intersections. The program ignores the `borderMeshes` of a city it loads, with a warning: a core migration should convert them (the Midtown Madness 2 one makes them rail elements through the same points, in the same clockwise order, so that their components stay on the same side).

## Automatic generation

"Create whole city terrain" creates one patch for each area enclosed by roads and intersections (by following their anchor chains, see [Core Roads](Core-Roads#settingsjson) and [Core Intersections](Core-Intersections#junction-files)) and a ring of patches around the whole road network. The new patches are created like manual ones (see above), with the texture, smoothing and internal point distance chosen in the dialog. The quality of the result depends on the anchors of the core's road and junction types: they must form closed loops around every block.
