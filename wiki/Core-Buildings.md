# Core Buildings

Buildings are generated by the program from a fixed structure: a **building line** is split into **buildings**, each building has up to four **sides** (front, left, right, back) and a roof, and each side is a grid of **blocks** arranged in floors and slices. The core defines the parameters of each level and the **block types** that fill the facades.

```
elements/
├── buildings/<type>/
│   ├── line_ui.json, line_parameters.json, line_settings.json
│   ├── building_ui.json, building_parameters.json, building_settings.json
│   └── side_ui.json, side_parameters.json, side_settings.json
└── buildingBlocks/<type>/
    ├── ui.json
    ├── parameters.json
    ├── settings.json
    └── components/<component>.json
```

All nine files of a building type are required (the `*_settings.json` files of lines and buildings are currently empty objects).

## Structure and built-in parameters

### Building line

A polyline of points placed by the user (or generated around a block). Points marked as dividing split it into buildings. Its type (the `type` property of the line state) also selects the type used by its buildings.

Built-in state properties: `type`, `height` (default building height), `frontOnly` (generate only the front side, as a facade along the line), `loop`, `invertDirection`, `projectToGround`, `roofTex` (texture of the roof covering the whole line when it is closed).

Built-in UI groups (`line_ui.json`): `mainGroup` (type, preset, list of buildings), `propertiesGroup` (the properties above), `loopGroup` (automatic closing with random building presets).

Line parameters can be `instanceSpecific`.

### Building

Built-in state properties: `front`, `left`, `right`, `back`, `top` (which sides and the roof are generated), `height`, `depth`, `fixAcuteAngles`, `topTexture`, and the states of the sides: `frontState`, `leftState`, `rightState`, `backState`.

Built-in UI group (`building_ui.json`): `mainGroup`.

### Side

Built-in state properties:

| Property | Description |
|---|---|
| `type` | Building type whose `side_*` files define this side's parameters. |
| `blockDict` | The blocks used by the side: a list of block states, each with a `type` (a block type name), a `listName` (shown in the list) and the parameters of the block type. Floors refer to blocks by index in this list. |
| `hasGroundFloor` | Whether the side has a ground floor. |
| `groundFloor` | `minHeight` and `Slices`: a list of `{bottom, middle, top, Width, Repetitions}`, where `bottom`, `middle` and `top` are block indices. The ground floor follows the slope of the terrain: the `bottom` block fills the space between the ground and the floor line, `middle` is the floor itself and `top` fills the remaining height up to `minHeight`. |
| `upperFloors` | A list of floors, each with a `height` and `Slices`: a list of `{block, Width, Repetitions}`. |
| `lowUpperFloorsCount`, `highUpperFloorsCount` | The first `lowUpperFloorsCount` upper floors are used once at the bottom of the building, the last `highUpperFloorsCount` once at the top; the floors in between are repeated as many times as needed to reach the building height. |

Slices are repeated (`Repetitions` times each, cycling through the list) while they fit in the side's length, then stretched horizontally to fill it exactly. Consecutive identical slices are merged into a single block whose `xMult` is the number of merged slices.

Built-in UI groups (`side_ui.json`): `mainGroup` (floors) and `blocksGroup` (block dictionary).

## `*_parameters.json`

Same format as for other elements (see [Parameters and UI](Parameters-and-UI)), evaluated once per line, building or side. The following definitions are read by the program and are therefore required:

| File | Variables | Used for |
|---|---|---|
| `line_parameters.json` | `uMult`, `vMult` | UV scale of the line's roof (world X/Z coordinates × multiplier). |
| `building_parameters.json` | `uMult`, `vMult` | UV scale of the building's roof. |
| `side_parameters.json` | `uMult`, `vMult` | UV scale of the facade blocks: passed to every block of the side. |

## `side_settings.json`

```json
{ "blockTypes": ["empty", "texture", "sliver"] }
```

`blockTypes` lists the block types that can be chosen for the blocks of this side.

## Block types

A block is one cell of a facade. Two block type names are handled directly by the program and must exist as folders (with at least a `ui.json`, `parameters.json` and `settings.json`) if they are used:

| Name | Behavior |
|---|---|
| `empty` | Generates nothing (a gap in the facade). |
| `texture` | A flat rectangle covering the cell, textured with the block's `assetName` parameter (which the type must define as a `texture` parameter). UVs: `(xMult × uMult, vMult)` at the bottom-left corner, `(0, 0)` at the top-right. Identical texture blocks are instanced, which keeps the exported data small. |

Any other block type is **parametric**: its mesh is generated from its components.

### `settings.json`

```json
{
    "alwaysDraw": false,
    "thumbnail": "assetName",
    "textures": ["assetName"],
    "texturesMapping": { "mesh": [0] },
    "components": [ { "name": "mesh", "condition": "true" } ]
}
```

| Key | Description |
|---|---|
| `thumbnail` | Name of the texture parameter whose texture is shown as the block's icon in the side editor (empty for none). |
| `alwaysDraw` | Recorded on the facades that contain such blocks (`Facade.hasAlwaysDraws`), but currently not used nor exported. |
| `textures`, `texturesMapping`, `components` | As for road types. Required for parametric blocks. |
| `mergeable` | Reserved, currently unused. |

### Component files

```json
{
    "localDefinitions": [],
    "mesh": {
        "vertices": ["vec3(0, y0, 0)", "vec3(1, y1, 0)", "vec3(0, 1, 0)", "vec3(1, 1, 0)"],
        "uvs": ["vec2(xMult * uMult, (1 - y0) * v3y(scale) * vMult)", "vec2(0, (1 - y1) * v3y(scale) * vMult)",
                "vec2(xMult * uMult, 0)", "vec2(0, 0)"],
        "faces": [0, 2, 1, 1, 2, 3],
        "facesTextures": [0, 0]
    }
}
```

The block mesh is described in a unit cell: X from 0 to 1 across the block, Y from 0 to 1 from the bottom to the top of the cell, Z perpendicular to the facade (in meters). The program then scales it to the cell size and places it on the facade.

* `faces` are triangles: three vertex indices per face. Indices refer to the vertices of the same component (the first vertex of every component has index 0), as for road components.
* `facesTextures` has one entry per triangle, an index into `texturesMapping[component]`.

### Block variables

| Variable | Type | Meaning |
|---|---|---|
| `y0`, `y1` | float | Bottom of the cell at its left (X = 0) and right (X = 1) edge, between 0 and 1. They are not 0 only for the bottom blocks of a ground floor on sloped terrain, which must follow the ground. |
| `xMult` | float | Number of identical slices merged into this block (for tiling the UVs). |
| `scale` | vec3 | Actual size of the block in meters (width, height, 1). |
| `uMult`, `vMult` | float | The UV multipliers of the side. |
| `localUp`, `localRight`, `localForward` | vec3 | The axes of the unit cell: `(0, 1, 0)`, `(1, 0, 0)` and `(0, 0, -1)`. |
| `worldUp`, `worldRight`, `worldForward` | vec3 | `(0, 1, 0)`, `(1, 0, 0)`, `(0, 0, 1)`. |

### Order of evaluation

For each block: the block type's parameters (read from the block's state) and static definitions, then the variables above, then the dynamic definitions, then, for each active component, its local definitions and its mesh. The variables above are set by the side, so they replace block definitions with the same name: the MM2 `sliver` block, for example, defines `uMult` and `vMult` as static definitions, but uses the side's values.
